# OCRFlow v1.6.5

## 大体积任务恢复记录

- 旧格式 Base64 解码改为固定大小分块，避免通过 `Uint8Array.from()` 将整个字符串展开为中间数组。解密阶段及时释放大体积临时引用。
- 字符串、原生异常和未知异常均显示实际错误原因，文件存在性检查也纳入读取错误处理。

## 恢复记录新格式

- 恢复记录改为 `ocrflow-tasks/index.json`（队列顺序与下一个任务编号）加 `ocrflow-tasks/tasks/<任务编号>/task.json`（单个任务）。保存时只重写内容有变化的任务。
- 图片、二进制数据和 64K 字符以上的文本写入任务目录下的 `files/`，每个文件只写一次，任务记录中只保存相对路径。
- 所有恢复文件通过临时文件原子写入，包括此前未使用临时文件的二进制资源和云端切片。
- 单个任务记录无法读取时，将其移到 `ocrflow-tasks/damaged/` 并提示，其余任务照常恢复。读到更新版本创建的记录时只提示，不覆盖、不删除。

## 不再保存密钥

- 任务设置中的 `apiToken`、`apiKey`、`token`、`deeplApiKey`、`deeplxToken`、`llmApiKey` 保存为其所在配置项的名称（如 MinerU Token、Marker Token、某个 AI 服务商），恢复时从当前配置读取。配置中找不到的值不保存，恢复后为空。
- 其余设置仍按入队时的快照保存，恢复后继续使用原来的服务、模型和参数。
- 记录不含密钥，改为本机明文文件，不再使用 AES-GCM 加密。恢复时仍需先解锁配置，以便读取密钥。

## 旧记录迁移

- 启动时发现 `queue.enc`，解锁配置后用原有方式解密读取，与新格式中的任务合并，冲突的任务编号重新分配，并同步更新前置识别引用。
- 新格式第一次保存成功后，删除 `queue.enc` 和 `resources/`。保存失败时旧记录保持不动。
- 降级到旧版本后再升级，旧版本期间写入的 `queue.enc` 会再次导入。

## 按步骤编号恢复

- 任务记录新增固定的步骤编号 `stage`：`submitting`、`submitted`、`processing`、`saving`、`saved`。编号发布后不再改名，恢复时据此判断任务进度，不再匹配界面文字。旧记录没有步骤编号时，沿用原来的判断方式。
- Marker、Datalab 和 MinerU 本机服务在提交前记录 `submitting`，拿到任务 ID 后记录 `submitted`。没有任务 ID 的 `submitting` 任务恢复后暂停，等待用户核对。
- 保存识别结果或译文前记录 `saving` 并立即保存，写入附件后记录 `saved`。停在 `saving` 的任务（包括一键整理的子步骤）恢复后暂停，提示检查附件后重试，避免重复附件。双引擎校勘在底稿保存后立即记录，避免重复保存底稿。
- 读到不认识的步骤编号时，任务暂停，等待用户确认。

## 验证

431 项插件测试通过。恢复测试覆盖：密钥不写入任何恢复文件且恢复后读取当前配置；未变化的任务不重写；资源只写一次并在失效后清理；单个记录损坏、更新版本记录；v1、v2 加密记录迁移和降级后再导入；在提交前、拿到任务 ID 后、保存附件前中断识别任务后的恢复状态。

开发期间，本机用分块解码实测读取约 846 MB 的旧恢复记录，恢复 15 项旧任务。新格式尚未在真实 Zotero 中验证。
