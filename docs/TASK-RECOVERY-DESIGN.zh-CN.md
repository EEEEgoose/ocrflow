# 任务断点续接设计（草案，计划用于 1.6.5）

状态：已在 1.6.5 实现。实现与本设计不同的地方见第 16 节。

## 1. 目标

Zotero 本身或 OCRFlow 插件更新时，如果还有任务没做完，重启后要能从中断的那一步接着做。具体要保证：

1. **不重复提交、不重复付费**：已提交到云端的识别任务不能再交一次，已经翻好的段落不能再请求一次。
2. **不丢已完成的工作**：已下载的识别结果、已完成的切片、已翻好的段落、已保存的附件都要保留下来。
3. **能接着往下做**：恢复后知道任务停在哪一步、下一步做什么，不依赖界面文字。
4. **记录大小不随内容增长**：读写恢复记录的耗时和内存，跟识别全文、图片、译文的大小无关。

Zotero 崩溃或被强制退出时尽量恢复，最多丢最近几秒的进度，但不能因此重复提交或产生重复附件。

不在本设计范围内：
- 跨设备同步任务
- 删除 Zotero 数据目录后的恢复
- 任务完成后的历史记录

## 2. 现状（1.6.x）

记录保存在 `<Zotero 数据目录>/ocrflow-tasks/`：
- `queue.enc`：整个队列序列化后用 AES-GCM 加密，密钥存在 Firefox 登录管理器里（[task-recovery.js](../task-recovery.js) `storageKey`）。
- `resources/`：v2 格式会把 64K 字符以上的字符串和所有二进制拆出来放在这里。
- `task-<id>-cloudState` 等目录：存放云端切片文件（`preserveTaskFiles`）。

做得对、要保留的：
- 插件更新、停用和 Zotero 退出时，`bootstrap.js` 的 `shutdown()` 会调用 `taskRecovery.shutdown()`，暂停任务、等待正在保存的操作完成，再保存一次。
- 有副作用的步骤前后已经调用 `checkpoint()`（即 `flush()`）：
  - PaddleOCR 切片提交前设置 `part.submitting`（[paddleocr.js:110](../paddleocr.js#L110)）
  - 云端上传前后设置 `uploadStarted`、`uploaded`（[recognition.js:283-289](../recognition.js#L283-L289)）
  - Datalab 拿到任务 ID 后立即保存（[datalab.js:44](../datalab.js#L44)）
- 提交结果没确认的任务（已提交、还没拿到任务 ID）恢复后停在"等待确认"，不会自动重交（[task-recovery.js:257-260](../task-recovery.js#L257-L260)）。
- 任务 ID 冲突时，给本次启动后新加入的任务重新编号，并同步修改 `requiredParseID`。

存在的问题：

| # | 问题 | 后果 |
|---|---|---|
| P1 | 每次保存都把整个队列重新序列化、加密、写入 | 记录越来越大，保存越来越慢；1.6.1 读取 846MB 的旧记录时内存不足 |
| P2 | 恢复时用正则匹配 `phase` 里的中文文字（如"提交 Marker 任务"），判断任务停在哪一步 | 以后改了这句话，旧任务就会被误判；而插件更新正好是本功能要应对的场景 |
| P3 | `settings`、`cancelSettings`、`displaySettings` 和 `organizeStages[].task.settings` 是完整的配置快照，含 `apiKey`、`apiToken`、`deeplApiKey`、`deeplxToken` | 记录必须加密；登录管理器里的密钥丢失后整份记录读不出来；配置解锁前无法显示待恢复的任务 |
| P4 | 只有一个主文件 | 一个任务的数据出错，所有任务都恢复不了 |
| P5 | 保存附件中途中断时，恢复后不知道附件是否已经写入 | 可能产生重复附件 |
| P6 | 二进制资源写入没有使用 `tmpPath` | 写到一半中断时，留下不完整的文件，并且因为"文件已存在"不会再重写 |

## 3. 设计原则

1. **记录只保存续接所需的状态**：外部任务 ID、切片进度、已完成的部分结果、队列顺序、所用服务的标识。
2. **大块内容只在产生时写一次**：写入任务目录下的文件，记录里只保存相对路径；能从 Zotero 附件重新读出的内容，只保存附件引用。
3. **不保存密钥**：恢复时按服务标识从配置中重新取得设置。没有密钥之后，记录不再加密。
4. **先写意图，再执行，再写结果**：所有有副作用的步骤（提交任务、保存附件、修改条目）都按这个顺序保存。
5. **步骤用固定编号表示，不用界面文字**：编号一旦发布就不再改名或改含义。

## 4. 存储布局

```
<Zotero 数据目录>/ocrflow-tasks/
  index.json                 队列顺序、nextID、格式版本
  tasks/
    <taskID>/
      task.json              单个任务的小记录（明文）
      files/                 本任务产生的大块内容，每个文件只写一次
        parsed-result.json
        part-0.bin
        images/...
  queue.enc                  旧格式，迁移完成后删除
```

`index.json` 示例：

```json
{"format": "ocrflow-tasks", "version": 3, "nextID": 42, "order": [37, 38, 41]}
```

读取规则：
- 以 `tasks/` 下的目录为准。目录存在但不在 `order` 里的任务，按 ID 顺序追加到队列末尾；`order` 里有、目录不存在的 ID 忽略。这样 `index.json` 和 `task.json` 不需要一起原子写入。
- 单个 `task.json` 读取失败时，只把这个任务标记为"恢复记录损坏"并保留目录，不影响其他任务。

写入规则：
- 所有文件都通过 `tmpPath` 原子写入，包括二进制文件（修复 P6）。
- `files/` 下的文件写完后不再修改。内容变化时换一个新文件名，再更新 `task.json` 中的引用，然后删除旧文件。
- 每次只写有变化的任务（见第 7 节）。

## 5. 任务记录格式

`task.json` 示例（逐段翻译任务）：

```json
{
  "id": 38,
  "kind": "translate",
  "schema": 3,
  "stage": "translating",
  "state": "running",
  "title": "Synthetic Paper",
  "attachment": {"libraryID": 1, "key": "ABCD1234"},
  "parentItem": {"libraryID": 1, "key": "EFGH5678"},
  "route": {"service": "openai-compatible", "modelID": "model-a"},
  "requiredParseID": 37,
  "translation": {
    "language": "zh-CN",
    "paragraphBudget": 1800,
    "units": "files/units-1.json",
    "done": "files/done-3.json"
  },
  "updatedAt": 1763190000000
}
```

字段分三类：

| 类别 | 内容 | 处理方式 |
|---|---|---|
| 身份与路由 | `id`、`kind`、`attachment`、`parentItem`、`requiredParseID`、`route` | 直接保存；Zotero 条目只存 `libraryID` + `key` |
| 进度 | `stage`、外部任务 ID、切片状态、各阶段是否完成 | 直接保存，通常只有几 KB |
| 大块内容 | 识别结果、切片文件、图片、分段原文、译文 | 写入 `files/`，记录里只存相对路径 |

`route` 只保存用于重新取得设置的标识。字段与现在 `retryParseQueueTasks` 保留的一致：`parserService`、`explicitService`、`markerSettings.apiType`、`apiMode`，以及标题翻译的 `service`、`targetLang`、`overwrite`、`modelID`。不保存任何密钥、Token 或服务地址中的凭据。

## 6. 步骤编号

每个任务记一个 `stage`，取代现在对 `phase` 文字的匹配（修复 P2）。所有任务类型共用一套基本编号，各类型的细分进度放在各自的字段里，比如云端识别的 `cloudState.parts`。

| `stage` | 含义 | 恢复时的处理 |
|---|---|---|
| `queued` | 还没开始 | 正常排队 |
| `submitting` | 正在提交外部任务，还没拿到任务 ID | 停在"等待确认"，用户核对服务端后再决定是否重交 |
| `submitted` | 已拿到外部任务 ID，正在等结果 | 按任务 ID 继续查询 |
| `downloading` | 正在下载结果 | 按任务 ID 重新下载 |
| `processing` | 本地处理（整理结构、校对、翻译段落等） | 从已完成的部分接着做 |
| `saving` | 正在写入 Zotero 附件或修改条目 | 先检查结果是否已经写入（见第 8 节），再决定是否重写 |
| `completed` | 已完成 | 不恢复，按现有规则清理 |

多切片任务（PaddleOCR、云端分片上传）的 `submitting` 继续记在每个切片上，沿用现有的 `part.submitting`、`uploadStarted` 字段，只是改为由 `stage` 和切片状态一起判断，不再匹配文字。

规则：
- 编号发布后不能改名或改含义。需要新步骤时只能新增编号。
- 读到不认识的编号时，任务停在"等待确认"，不猜测下一步。

实施时需要把现有各识别服务通过 `onStatus` 报告的 `phase` 逐个对应到上表，确认没有遗漏的步骤。

## 7. 保存时机

1. **立即保存**：每次进入 `submitting`、拿到外部任务 ID、切片完成、进入 `saving`、附件写入完成时，立即保存这个任务。现有的 `checkpoint()` 调用点保留，改为只保存当前任务。
2. **延迟保存**：进度条、状态文字这类变化沿用 5 秒延迟保存（`schedule()`），只写有变化的任务。
3. **变化跟踪**：维护一个 `dirty` 集合，记录有变化的任务 ID。调用 `checkpoint(task)` 或 `schedule(task)` 时把任务加进去；保存时只写这些任务，以及队列顺序变化时的 `index.json`。
4. **串行写入**：沿用现有的 `serial` Promise 链，同一时间只有一次保存在进行。

这样每次保存只写几 KB，跟识别结果的大小无关（修复 P1）。

## 8. 避免重复附件

保存附件分三步：
1. 写入 `stage: "saving"`，同时记录要写入的父条目、文件名和 `saveStartedAt`。
2. 写入附件。
3. 写入 `resultAttachment`（附件引用）和下一个 `stage`。

恢复时，如果任务停在 `saving`、但没有 `resultAttachment`，先在父条目的子附件里查找同名、且添加时间不早于 `saveStartedAt` 的附件：
- 找到：直接采用这个附件，不再重写。
- 没找到：重新保存。

修改条目元数据（书目、标题翻译、重命名）的步骤同理，先写意图，修改后写结果。现有的 `metadataCompleted`、`renameCompleted` 已经是这种做法，保留即可。

## 9. 设置与密钥

把 `retryParseQueueTasks` 里重新取得设置的逻辑提取为 `resolveTaskSettings(task)`，在两处使用：
- 用户手动重试时（现有行为）
- 从记录恢复任务时（新增）

保存时，`settings`、`cancelSettings`、`displaySettings` 都不写入记录，只写 `route`。恢复后由 `resolveTaskSettings` 重新生成；`cancelSettings` 和 `displaySettings` 按现有规则从 `settings` 推出（[docflow.js:674-675](../docflow.js#L674-L675)、[collation.js:18](../collation.js#L18)）。

这样一来：
- 记录里没有密钥，可以用明文保存（修复 P3）。识别结果本来就以明文附件存在 Zotero 文库里，恢复记录明文保存不会多出新的暴露面。
- Zotero 启动后不用等配置解锁就能读出记录，在任务侧栏显示有哪些任务待续接；配置解锁、取得设置后再继续执行。

需要注意：用户在两次启动之间改了配置（换了模型或服务地址）时，恢复后会使用新配置。这和现在手动重试的行为一致。只有一种情况需要拦截：外部任务 ID 属于原来的服务，而新配置换成了另一个服务。这时要让任务停在"等待确认"，而不是去新服务查询这个任务 ID。为此 `route` 里要额外保存服务地址的主机名，用来比对。

## 10. 恢复流程

1. 启动时读取 `index.json` 和各 `task.json`，不需要密钥。
2. 恢复 Zotero 条目引用。来源条目已删除的任务标记为失败（沿用现有规则）。
3. 按第 6 节的规则确定每个任务的状态，在侧栏显示出来。
4. 等配置解锁后，对每个任务调用 `resolveTaskSettings`，按第 9 节检查服务是否一致，然后开始处理队列。
5. 大块内容在任务真正开始执行时才读取，不在启动时全部读入内存。

## 11. 迁移与版本兼容

**从 `queue.enc` 迁移**
1. 启动时如果发现 `queue.enc`，等配置解锁后用现有的 `read()` 逻辑解密读取。
2. 把每个任务拆成新格式写入 `tasks/`，大块内容写入 `files/`，去掉设置快照，只保留 `route`。
3. 全部写入后重新读取一遍，确认能读出相同数量的任务，再删除 `queue.enc`、`resources/` 和旧的 `task-<id>-*` 目录。
4. 迁移失败时保留 `queue.enc` 不动，侧栏显示错误。下次启动时重试迁移。
5. 登录管理器中的恢复密钥在 `queue.enc` 删除之后再移除。

**降级到 1.6.x**
- 旧版本不认识 `tasks/`，只会忽略它，不会删除。
- 旧版本运行期间可能重新生成 `queue.enc`。再次升级时，按上面的流程把其中的任务导入，导入时遇到 ID 冲突按现有规则重新编号。

**以后的版本**
- `index.json` 的 `version` 表示整体格式，`task.json` 的 `schema` 表示单个任务的格式。
- 新版本负责迁移旧格式。旧版本读到更高的版本号时只提示，不覆盖、不删除文件（沿用现有行为）。

## 12. 关停与崩溃

| 情况 | 会不会调用 `shutdown()` | 依靠什么保存 |
|---|---|---|
| 插件更新、停用 | 会，并且通常会等它执行完 | `shutdown()` 最后一次保存，加上第 7 节的立即保存 |
| 正常退出 Zotero | 会调用，但还不确定 Zotero 是否等这个异步函数执行完 | 主要依靠第 7 节的立即保存 |
| 崩溃、强制退出、断电 | 不会 | 只能依靠第 7 节的立即保存和 5 秒延迟保存 |

所以正确性不能依赖 `shutdown()`：只要第 7 节的立即保存做到了，任何时候中断都不会重复提交，最多丢掉最近几秒的进度信息。`shutdown()` 只是让正常退出时的进度更完整。

## 13. 测试计划

新增 `tests/task-recovery-resume.test.cjs`，用内存中的 `IOUtils` 替身模拟文件系统，用替身服务模拟外部任务。对每类任务分别在以下位置"中断"：保留当前的文件系统，丢弃内存状态，重新加载模块并恢复。

| 中断位置 | 断言 |
|---|---|
| 进入 `submitting` 之后、拿到任务 ID 之前 | 恢复后停在"等待确认"，没有新的提交请求 |
| 拿到任务 ID 之后 | 恢复后只发查询请求，没有新的提交请求 |
| 部分切片完成 | 已完成的切片没有被重新请求 |
| 进入 `saving` 之后、附件写入之前 | 恢复后写入一个附件 |
| 附件写入之后、写入 `resultAttachment` 之前 | 恢复后采用已有附件，附件总数不变 |
| 逐段翻译做到一半 | 已翻好的片段没有被重新请求 |
| 文件写到一半（模拟 `tmpPath` 文件残留） | 读取的仍是上一次完整的内容 |

另外再测：
- 记录大小：识别结果从 1KB 增加到 10MB 时，每次保存写入的字节数基本不变。
- 记录中没有密钥：保存后扫描 `tasks/` 下的所有文件，找不到测试用的合成密钥。
- 迁移：用合成数据生成 v1、v2 的 `queue.enc`，迁移后任务数量、进度和依赖关系不变；迁移中途失败时 `queue.enc` 仍然保留。
- 不认识的 `stage`：任务停在"等待确认"。
- 换了服务：外部任务 ID 不会发给新服务。

真实环境验证（按 [VALIDATION.md](../VALIDATION.md) 的方式记录）：
1. 云端识别进行中更新插件，重启后任务继续查询原任务。
2. 识别进行中直接退出 Zotero，重新打开后任务停在正确的步骤。确认第 12 节表中"正常退出"一行的情况。
3. 识别进行中强制结束 Zotero 进程，重新打开后没有重复提交。

## 15. 待确认的问题

1. 正常退出 Zotero 时，`shutdown()` 里的异步保存是否会执行完？需要在 macOS 和 Windows 上实测。
2. 已完成的任务要不要保留在记录里？现在会保留一份去掉大块内容的记录，用于在侧栏显示。建议保留最近若干个，或者保留到用户清除为止。
3. 第 8 节靠"同名 + 添加时间"判断附件是否已写入，同一父条目下有同名附件时可能误判。是否需要在附件上加一个标记（比如写入任务 ID），具体做法待定。
4. 本机服务（本机 MinerU、本机 Marker）的任务在 Zotero 重启后是否还在运行，各服务的情况要逐个确认；不在运行的，恢复时按"已提交但结果丢失"处理。
5. 明文记录中保留的服务地址主机名和文献标题，是否可以接受？它们和 Zotero 文库中已有的信息相当。

## 16. 实现与设计的差异（1.6.5）

1. **设置与密钥（第 9 节）**：没有改为恢复时整体重新生成设置。任务仍保存入队时的设置快照，只把密钥字段（`apiToken`、`apiKey`、`token`、`deeplApiKey`、`deeplxToken`、`llmApiKey`）替换为密钥所在配置项的名称，例如 `pref:marker.token` 或 `provider:<服务商 ID>`，恢复时读取该配置项的当前值。
   - 这样恢复后仍使用原来的服务地址、模型和参数，与 1.6.0 的恢复行为一致。`cancelSettings`、`displaySettings` 和对照识别 B 的设置也能原样恢复，不会把任务 ID 发给别的服务，所以不再需要第 9 节的主机名比对。
   - 配置中找不到对应值的密钥不保存，恢复后为空，任务会因缺少密钥失败，用户可重试。
   - 用户修改了某个配置项的服务地址后，恢复的任务仍用快照中的旧地址，配合该配置项的新密钥。
2. **解锁前显示任务（第 10 节）**：没有实现。恢复仍等配置解锁后进行，因为密钥需要从配置读取。解锁前侧栏继续显示"配置解锁后恢复未完成任务"。
3. **避免重复附件（第 8 节）**：没有按"同名 + 添加时间"查找附件。停在 `saving` 的任务一律暂停，提示用户检查附件后重试，重试时重新保存。正常更新、退出时 `shutdown()` 会等保存完成，所以只有崩溃时才会出现这种情况。第 15 节第 3 个问题因此不再需要解决。`saving` 只覆盖识别结果和译文附件，总结、书目、标题译文沿用原有的完成标记。
4. **步骤编号（第 6 节）**：`downloading` 没有单独使用。下载仍算 `submitted`，恢复时按任务 ID 继续查询并重新下载。
5. **存储布局（第 4 节）**：云端切片目录 `task-<id>-cloudState` 等仍放在 `ocrflow-tasks/` 下，没有移入 `tasks/<id>/`，清理规则不变。`files/` 下的资源文件按内容复用文件名，不再变化的文件不会重写。损坏的任务记录移到 `ocrflow-tasks/damaged/`，不再留在原目录。
6. **迁移（第 11 节）**：新格式保存成功后直接删除 `queue.enc`，没有先读取一遍做验证，因为每个文件都是原子写入，任何一步失败都会在删除旧记录之前中止。登录管理器中的旧恢复密钥没有删除：它不再用于加密任何内容，保留它可以让降级后的旧版本继续使用。
